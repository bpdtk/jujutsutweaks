# JujutsuTweaks —— 咒灵操术储物维度优化

> 对应 `docs/01-咒灵操术-跨版本diff报告.md` 的「方案乙」：支持 v49 / v49.1 / v50 / v50.1 / v51，不做 v48。
>
> | 项 | 值 |
> |---|---|
> | 显示名 | JujutsuTweaks |
> | modId | `jujutsutweaks`（FML 强制全小写） |
> | 包名 | `com.jujutsutweaks` |
> | 备注 | 优化夏油杰（咒灵操术）在储物维度堆积大量咒灵时的性能开销，兼容 JujutsuCraft v49 - v51 |

---

## 一、这个补丁到底做了什么

一句话：**让存放在咒灵储物维度里的咒灵"暂停"，不再每 tick 消耗计算。**

它们没有被删除、没有变成数据、没有挪走。还是原来那些实体，还站在原来的坐标上，
`/execute in jujutsucraft:cursed_spirit_manipulation_dimension run tp @s ...` 照样能找到它们，
夏油杰的取出、释放、治疗、漩涡全部照常工作 —— 只是它们**不再 tick**。

---

## 二、为什么这样做能躲开 MCreator 重新打包的坑

你担心的是这件事：主体每次用 MCreator 重新打包，哪怕功能一行没改，签名也可能变，
所以按"类名 + 方法名"去改主体代码的附属（比如 jujutsuslop 系）会一个版本一个版本地失效。

**本补丁一个主体类都不碰。**

| | 传统附属的做法 | 本补丁的做法 |
|---|---|---|
| 注入目标 | 主体的 `Test1Procedure` / `EntityActiveProcedure` 等 | **原版 Minecraft 的 `ServerLevel.tickNonPassenger`** |
| 依赖什么 | 类名、方法名、方法描述符、NBT 键 | **只依赖一个字符串：维度 ID** |
| 主体重新打包 | 签名一变就崩 | 无影响 |
| 与其他附属冲突 | 抢同一个注入点 | 注入点完全不同 |

维度 ID 是 `jujutsucraft:cursed_spirit_manipulation_dimension`。
diff 报告里已验证：**v48 到 v51 六个版本这个 ID 一字未变**，而且维度、维度类型、群系三个 JSON 文件
在六个版本里逐字节相同。也就是说，只要作者不改维度 ID，这个补丁就一直是有效的。

> 顺带一个设计上的好处：因为这个 ID 在 v48 里也一样，技术上本补丁对 v48 大概率也有效。
> 但按你的决定，v48 不纳入支持范围，`mods.toml` 里把依赖下限写成了 `[49,)`，
> 装在 v48 上会直接被 Forge 拦下，避免出现"能装但没测过"的灰色地带。

## 三、原理（为什么选这个注入点）

### 3.1 服务端每个实体每 tick 只有一个入口

`ServerLevel#tickNonPassenger(Entity)` 是服务端遍历实体列表时对每个实体调用的方法。
在这个方法的**最开头**取消掉，等于：

- 原版 `LivingEntity.tick()` 整段不执行 → 物理、碰撞、药水、着火、窒息、消失检查、同步全部省掉
- 主体模组的 `EntityActiveProcedure`（挂在 `LivingTickEvent` 上）也不会触发
  —— 因为那个事件是在 `LivingEntity.tick()` **内部**发出的，实体不 tick，事件自然不发

这就是 diff 报告里「第 2 层 + 第 3 层」两个卡顿来源，一次全解决。

### 3.2 为什么不是注入 `Entity#tick`

`Entity#tick` 是几乎所有性能模组（Canary、ModernFix 之类）都会注入的地方，冲突概率高。
`ServerLevel#tickNonPassenger` 冷门得多，注入方式又是 `@Inject(at = HEAD, cancellable = true)`，
即使别人也注入了同一个方法，多个 HEAD 注入是可以共存的，不会互相顶掉。

### 3.3 为什么冻结不会把存储逻辑弄坏

关键在于：**实体不 tick ≠ 实体不存在**。

- `level.getEntities(...)` 走的是 `EntityLookup` 的实体索引，和 tick 完全无关 → 查得到
- 取出时 `teleportTo` 把它送出维度，下一 tick 就恢复正常
- 治疗逻辑是直接 `setHealth`，不依赖实体 tick
- `NoAI` / `Invulnerable` / `PersistenceRequired` 这些标记是存档数据，冻结不影响

### 3.4 完全不写存档

冻结是**纯运行时行为**，不往任何实体写 NBT、不往存档写标记。
删掉本模组，所有咒灵立刻恢复 tick，存档零残留。

## 四、安装与配置

### 4.1 安装

把 `build/libs/jujutsutweaks-1.0.0.jar` 丢进 `mods/` 即可。**只需装在服务端**。

客户端不装也能进服（`displayTest="IGNORE_SERVER_VERSION"`），单人游戏时客户端本身就是服务端，自动生效。

### 4.2 配置

首次启动后生成 `config/jujutsutweaks-common.toml`：

```toml
[storage]
    # 冻结储物维度内实体的 tick。
    # 关闭后本模组不产生任何效果，可用来排查兼容问题。
    freezeStoredSpirits = true

    # 每 30 秒在服务端日志输出一次冻结统计。
    logSummary = false
```

### 4.3 验证

游戏内（需要 OP / 权限等级 2）：

```
/jujutsutweaks status
```

输出示例：

```
冻结: 开 | 上一 tick 跳过实体: 137 | 累计跳过实体 tick: 412233 | 储物维度: 已加载
```

- **上一 tick 跳过实体 137** = 这个维度里存着 137 个咒灵，每 tick 全部被跳过
- 如果这个数字一直是 0，说明要么没存咒灵，要么配置被关了

也可以开 `logSummary = true` 看服务端日志，每 30 秒一行。

## 五、边界与风险（写清楚，免得踩坑）

| 情况 | 行为 | 是否需要处理 |
|---|---|---|
| 玩家用命令进入该维度 | **不受影响**，玩家永远不冻结 | 无需处理 |
| 玩家把宠物/其他实体带进该维度 | 会被一起冻结（这个维度本质就是储物柜） | 属预期行为 |
| 其他附属也把实体存在这个维度 | 同样被冻结，且它们大概率因此受益 | 属预期行为 |
| 主体模组改了维度 ID | 补丁静默失效（不崩、不报错） | 用 `/jujutsutweaks status` 看「储物维度: 未加载」即可发现 |
| 与其他性能模组共存 | 注入点不同，不冲突 | — |
| 移除本模组 | 所有实体立刻恢复 tick | — |

**唯一需要留意的**：如果某个附属依赖"储物维度里的咒灵需要持续 tick 来维持状态"（比如靠 tick 刷新某个 buff），
冻结会让那个状态停住。遇到这种情况把 `freezeStoredSpirits` 改成 `false` 即可，不影响存档。

## 六、我评估过但**没有**做的优化

| 项目 | 为什么不值得做 |
|---|---|
| 把 `forceload add` 改成只执行一次 | 要改主体类（`Test1Procedure` 等 11 处），增加耦合；而且它只在收服瞬间执行，不是热点 |
| 优化 `HealCurseSpiritManipulationProcedure` 的 256³ 扫描 | 实测那个 AABB 只覆盖到 1 个已加载区块（其余 15×16 个区块根本没加载，直接跳过），开销极小 |
| 把咒灵改成纯数据存储（NBT 化） | 要重写 `Test1` / `Test2` 和全部 11 个调用点，等于重做技能，且必然破坏其他附属 |
| 定期卸载储物区块 | 主体靠 `getEntities` 找咒灵，区块一卸载就查不到，会直接破坏存储功能 |

**结论：单点冻结就能吃掉 90% 以上的收益，其余都是负收益或高风险。**

### 9.3 过程中修掉的两个坑

1. **refmap 不生成**：MixinGradle 只*检查*注解处理器、不自动添加。少了
   `annotationProcessor "org.spongepowered:mixin:0.8.5:processor"`，refmap 就不存在，
   **线上会静默失效**（不崩、不报错、就是不干活）。第一版正是这样，已补上。
2. **中文备注乱码**：`gradle.properties` 按 ISO-8859-1 读取，中文放进去会被写坏；
   加上 `processResources` 默认用平台编码（GBK）读写，双重破坏。已改为
   **备注直接写在 `mods.toml` 里 + `filteringCharset = 'UTF-8'`**。
3. **配置事件未过滤**：`ModConfigEvent` 会对**所有模组**的配置广播，原实现没过滤 modId，
   若别的模组配置先加载会去读我们尚未载入的 spec → `IllegalStateException`。已加 modId 过滤。

> 两次实跑都因为本地缺 `playeranimator` 前置，临时把主体依赖改成可选、只验证注入本身；
> 验证完已还原为 `mandatory=true` 并重新打包，当前 `build/libs` 里的是正式版。

## 十、几个需要你知道的细节

1. **改名要点**：FML 强制 modId 全小写，所以内部 ID 是 `jujutsutweaks`，而显示名 `JujutsuTweaks`
   可以保留驼峰 —— 玩家在模组列表里看到的是显示名。改名需要同步改动：
   `gradle.properties`（mod_id / mod_name / mod_group_id / mod_description）、
   Java 包名、`jujutsutweaks.mixins.json`（文件名 + package + refmap）、
   `assets/<modid>/lang/` 路径与翻译键。`build.gradle` 里的 refmap 名字是 `${mod_id}.refmap.json`，会自动跟随。

2. **主体 ver50.1 的版本号是错的**：它的 `mods.toml` 里写的是 `version="50"`，和 ver50 一模一样
   （作者忘了改）。所以 FML 眼里 50 和 50.1 是同一个版本，依赖范围 `[49,)` 对两者都成立。

3. **本补丁对主体版本号不敏感**：`[49,)` 只是个门禁，真正的兼容性来自「维度 ID 不变」。
   主体以后出 v52、v53，只要不改维度 ID，本补丁不用重新编译就能用。

4. **`temp/` 可以随时整个删掉**：里面只有分析产物和构建日志，删了不影响项目，
   需要时重新解包反编译即可（`tools/` 里的 vineflower 还在）。
